# 关闭已确认输入

把“发现归档候选”“人工批准”和“关闭来源”分为三个阶段。本技能可以生成未批准候选，也可以执行已经批准的迁移；不得把候选发现等同于归档授权。

## 开始前读取

依次读取：

1. 根目录 `AGENTS.md` 和 `AI-RUNBOOK.md`。
2. `知识库规则/SCHEMA.md`、`00-收件箱/收件箱说明.md`。
3. `知识库规则/自动化/已确认输入归档配置.md`。
4. `01-驾驶舱/归档审批.md`。
5. 获批条目的属性、AI处理区、相关衍生结果、目标目录说明和来源同步索引。
6. 处理外部来源时读取[来源适配规则](references/source-adapters.md)，只加载本批涉及的来源段落。

默认不扫描 `99-归档/` 正文全集。只读取目标冲突检查所需的文件名、属性或明确目标。

## 运行模式

- 默认`discover_and_execute`：先刷新待批准候选，再执行已批准条目。
- `discover_only`：只生成或补充待批准候选，不移动文件。
- `execute_only`：只预检和迁移已批准条目，不发现新候选。

定时任务默认使用`discover_and_execute`。发现阶段与执行阶段分别统计，任一阶段零项都要如实报告。

## 发现归档候选

按以下顺序渐进读取，不扫描整个收件箱正文：

1. 各来源同步索引中的本地路径、来源ID、本地状态和处理状态。
2. 最近的每日整理、分流、来源包审计和知识提炼报告。
3. 仅对候选来源读取frontmatter、摘要与AI受控区；需要确认目标建议时才读取相关项目或领域主页。

满足以下条件的来源可进入“待批准”，但不代表已经满足执行门槛：

- 来源仍位于`00-收件箱/`，且未被标记为missing、deleted、moved或已关闭。
- 已经过对应日处理，或存在明确处理记录；纯同步但尚未整理的来源不生成候选。
- 不存在相同`closure_id`的待批准、已批准或已关闭记录。
- 能识别稳定来源ID和来源粒度；飞书按完整来源包生成一条候选，浮墨按单条memo生成。

使用`closure_id: close-<source>-<稳定来源ID>`。将新候选追加到审批页的`ARCHIVE_APPROVAL_CANDIDATES`受控区，格式为：

```markdown
- [ ] #归档批准 [[来源笔记或来源包主笔记]] <!-- closure_id: close-来源-稳定ID -->
  - 来源类型：flomo | feishu | xiaohongshu | douyin | obsidian-direct | other
  - 处理方式：建议值 / 待确认
  - 目标位置：自动 / Auto
  - 衍生结果：[[相关卡片或报告]] / 不适用 / Not applicable
  - 审批状态：pending / 待批准
  - 待确认：具体缺口 / 无 / None
  - 索引：[[来源同步索引]] / 不适用 / Not applicable
  - 候选生成时间：YYYY-MM-DDTHH:mm:ss+时区
  - 确认时间：自动 / Auto
```

发现阶段只能追加新`closure_id`或补充完全空白的建议字段。不得勾选候选，不得在发现阶段把`pending`改为`approved`，不得覆盖用户修改的目标、处理方式、待确认、确认时间或复选框状态。来源不再符合候选条件时保留记录并追加`候选状态：stale / 已失效`，不静默删除。

## 唯一授权入口

执行阶段只处理 `01-驾驶舱/归档审批.md` 中带稳定`closure_id`、包含`#归档批准`且已经勾选的条目：

```markdown
- [x] #归档批准 [[来源笔记]] <!-- closure_id: close-来源ID -->
  - 处理方式：建议值 / 待确认
  - 目标位置：自动 / Auto
  - 衍生结果：[[相关卡片或报告]]
  - 审批状态：pending / 待批准
  - 确认时间：自动 / Auto
```

复选框勾选表示用户批准移动这一条来源记录，并授权技能按知识库预设补齐批准状态、确认时间和目标；不代表批准删除。仅在对话中说“整理完成”、来源状态变为 processed、候选任务已转换、文章卡已生成或超过一定天数，都不构成归档授权。

执行阶段遇到已勾选条目时：

1. 自动把`审批状态`写为`approved / 已批准`。
2. 优先读取条目行尾的Tasks完成日期`✅ YYYY-MM-DD`作为勾选日期并写入`确认时间`。
3. 如果没有完成日期且确认时间为空，以本次自动化首次发现勾选的本地时间作为确认时间，同时在条目行尾补`✅ YYYY-MM-DD`。不得根据文件修改时间倒推。
4. 按“目标预设”解析并写入`目标位置`；人工已经填写且安全有效的唯一目标作为显式覆盖。

## 统一授权与安全门槛

飞书、浮墨、小红书、抖音、Obsidian直写、通话记录和附件统一使用：

1. 审批行已勾选并包含`#归档批准`。
2. `closure_id`稳定且唯一。
3. 来源链接可解析，来源文件或来源记录存在于收件箱。
4. 技能能够依据预设解析出知识库内唯一目标。
5. 必要衍生结果存在，或明确为“不适用 / Not applicable”。
6. 目标无路径、同名或来源ID冲突。
7. 来源索引或台账可安全更新；无索引来源可明确识别。
8. 不涉及删除、覆盖或扩大到审批行之外的文件。

审批状态、确认时间、处理方式为“待确认”、目标位置为“待确认”，以及来源中的业务待确认内容，都不再是授权失败条件；技能在执行阶段补齐机器字段，业务待确认内容随来源保留并写入报告。来源适配器只能增加来源包、附件和索引完整性检查，不能降低以上安全门槛。

## 预检

逐条验证，任一条件失败就跳过并报告：

- `closure_id` 存在且在清单、报告和来源索引中唯一。
- 来源位于 `00-收件箱/`，文件存在且未被其他流程移动。
- 按预设解析唯一目标；目标位于知识库内且符合目录路由。
- 要求的闪念卡、文章卡、正式任务、知识笔记或处理报告已经存在；不适用时清单明确写“无”。
- 来源中的候选待办和待确认内容原样保留，不因归档勾选而转换、删除或改写；在关闭报告中列出。
- 来源索引可识别且能安全更新；飞书来源包必须完整并整体迁移。
- 目标不存在同名文件、相同来源 ID 或其他冲突。

先生成预检结果。单批遵守配置上限；超过上限时分批，不扩大授权范围。

## 路由

按以下优先级自动解析目标：

1. 审批条目人工填写了知识库内安全、唯一且与路由一致的目标时，作为显式覆盖。
2. 来源或处理结果已有明确且唯一的项目归属：迁入对应项目的`材料/`或`会议/`。
3. 已明确为内容素材且主题唯一：迁入`06-素材库/`对应主题。
4. 已明确为日志且目录唯一：迁入`05-日志/`对应目录。
5. 其他情况使用保留备查预设：
   - `flomo` → `99-归档/浮墨/保留备查/`
   - `feishu` → `99-归档/飞书妙记/保留备查/`
   - `xiaohongshu` → `99-归档/小红书/保留备查/`
   - `douyin` → `99-归档/抖音收藏/保留备查/`
   - `obsidian-direct`、通话、附件和`other` → `99-归档/其他/保留备查/`

不得只凭AI猜测把来源路由到项目、素材或日志；证据不足时使用保留备查预设。

“删除候选”不在无人值守归档范围。删除必须由用户在当前任务中再次明确授权，并按知识库删除规则执行。

## 执行顺序

1. 为本批记录来源路径、预设目标路径、来源 ID、索引位置和相关双链。
2. 回填`审批状态：approved / 已批准`、确认时间、自动目标和目标解析依据。
3. 移动来源文件；成组来源一次整体移动。不得覆盖目标文件。
4. 更新迁移后文件的 `status`、`updated` 和适用的关闭信息；保留原文与人工区域。
   - `status` 按最终路由写为 `done` 或 `archived`，并同步维护 `status_label`。
   - 浮墨等带独立 AI 处理状态的来源，迁移成功后把 `ai_processing_status` 收口为 `done`，同步写入 `ai_processing_status_label: 已完成 / Done`；不得让已归档来源继续显示为 `waiting_confirmation`。
   - 已含 `#已转正式任务`、`promoted_to` 和 `promoted_at` 的候选，把 AI 受控区内的候选展示状态收口为“已转正式任务”；不得改写正式任务的完成状态。
   - 来源中的“归档审批”“最终归属”等机器维护字段同步写为“已关闭”和实际目标；业务事实、人工备注与仍需后续处理的事项原样保留。
5. 按[来源适配规则](references/source-adapters.md)更新来源同步索引中的本地相对路径，并记录 `local_state: moved`、`local_state_label: 已迁移 / Moved`、`moved_at`、`destination_type`和`destination_type_label`。索引不删除历史来源 ID。浮墨同步技能不再接受迁移清单，本步骤只能由本技能执行。
6. 修复本次迁移直接造成的双链失效；至少搜索原收件箱相对路径、来源 ID 和 `candidate_id`，把项目、领域、衍生结果及本次审批记录中的活动链接更新到新路径。历史执行报告中的原路径作为审计证据保留，不改写；不顺便重写无关笔记。
7. 验证来源已不在收件箱、目标文件存在、索引指向目标且衍生结果仍可追溯。
8. 在审批行追加 `#已归档`、`closed_to`、`closed_at`和`关闭状态：closed / 已关闭`。只有全部验证成功后才写成功标记。随后把完整审批记录从 `ARCHIVE_APPROVAL_CANDIDATES` 的“等待批准”受控区移动到页面“已关闭”区；保持原 `closure_id`、确认日期和审计字段不变，不复制记录。
9. 生成 `07-AI产出/整理报告/YYYY-MM-DD-已确认输入关闭报告.md`，列出成功、跳过、失败、原路径、目标路径、目标解析依据、确认时间来源和索引更新结果。

报告还要列出发现阶段的扫描索引数、处理记录数、新增候选数、重复跳过数、失效候选数和仍缺少目标的候选数。

部分失败时保留可恢复证据，不把审批项标成成功；能够安全回退本次单条移动时回退，不能安全回退时立即停止该条并报告人工处理步骤。

## 幂等与完成检查

- 已含 `#已归档`、`closed_to` 和 `closed_at` 的审批项只审计，不重复移动。
- `ARCHIVE_APPROVAL_CANDIDATES` 受控区只包含未关闭候选：不得残留 `#已归档`、`关闭状态：closed / 已关闭`或已勾选记录；关闭记录只保留在“已关闭”区。
- 来源、目标和索引三处状态一致；文件不再残留在收件箱。
- 已归档来源不得保留 `ai_processing_status: waiting_confirmation`；已转换候选不得继续显示“候选状态：待确认”。
- 本次迁移直接影响的活动笔记不得继续链接旧收件箱路径；历史报告中的原路径可保留用于审计。
- 原始内容未改写，来源 ID 和历史索引未丢失。
- 飞书来源包未拆分；浮墨单条 memo 仍对应唯一 Markdown。
- 未勾选和删除候选均未处理；目标不唯一时已使用来源保留备查预设。
- 报告数量与实际移动数量一致。
- 新发现候选真实出现在审批页，状态为`pending / 待批准`且未勾选；重复运行不产生相同`closure_id`。
- 发现阶段没有改变任何人工审批字段或触发迁移。
